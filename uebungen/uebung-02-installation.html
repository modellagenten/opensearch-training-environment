Übung 2: OpenSearch-Umgebung starten & erste Schritte [Beide]

Einleitung

In dieser Übung starten wir die OpenSearch-Schulungsumgebung mit Docker Compose. Die Umgebung enthält einen 2-Node-Cluster mit OpenSearch 3.7.0, OpenSearch Dashboards, Logstash sowie Prometheus und Grafana für das Monitoring. Beim ersten Start werden außerdem automatisch zwei Datensätze geladen, mit denen wir in den folgenden Übungen arbeiten. Nach dem Start machen wir erste Schritte mit der REST API und indexieren unsere ersten Dokumente - die Produktdaten aus Übung 1 kommen jetzt in den Cluster.

Lernziele

  • Docker-Compose-Umgebung für OpenSearch vorbereiten, starten und prüfen
  • Cluster-Status, Nodes und Indizes mit der REST API abfragen
  • Die vorgeladenen Datensätze verifizieren
  • Erste Dokumente über die REST API und die Bulk API indexieren
  • Dev Tools Console in OpenSearch Dashboards nutzen
  • Monitoring-Stack (Prometheus, Grafana) verifizieren

Voraussetzungen

  • Übung 1 abgeschlossen
  • Docker mit Compose v2 installiert (Docker Desktop oder Docker Engine)
  • Mindestens 8 GB RAM für Docker verfügbar
  • Ports 3000, 5044, 5601, 9090, 9200 und 9600 frei
  • Netzzugang beim ersten Start: Die Node-Images werden lokal gebaut und laden dabei das Prometheus-Exporter-Plugin von GitHub

Aufgabe

Teil 1: Umgebung vorbereiten und starten

  1. Wechselt in das Wurzelverzeichnis der Schulungsumgebung - dort liegt die docker-compose.yml:

    cd opensearch-training-environment
ls docker-compose.yml env.example

  2. Legt die .env-Datei an - sie ist nicht im Repository enthalten:

    cp env.example .env

    Die Datei enthält unter OPENSEARCH_PASSWORD das Admin-Passwort. Notiert euch den Wert, ihr braucht ihn gleich für den Login.

    Wichtig: Ohne .env bleibt OPENSEARCH_INITIAL_ADMIN_PASSWORD leer, und die Nodes starten seit OpenSearch 2.12 gar nicht.

    Wenn ihr das Passwort ändert, müsst ihr es auch in data/prometheus.yml anpassen - sonst kommt Prometheus nicht mehr an die Metriken.

  3. Startet die Umgebung:

    docker compose up -d

    Der erste Start dauert mehrere Minuten, weil die Node-Images gebaut werden. Danach geht es in etwa einer Minute.

  4. Prüft, ob alle Container laufen:

    docker compose ps

    Ihr solltet 6 laufende Container sehen: opensearch-node1, opensearch-node2, opensearch-dashboards, logstash, prometheus, grafana.

  5. Es gibt einen siebten Container, den ihr nur mit -a seht:

    docker compose ps -a

    opensearch-init lädt die Beispieldaten und beendet sich danach. Ein Status wie Exited (0) ist hier also kein Fehler, sondern das erwartete Ergebnis.

  6. Falls ein Container nicht startet, prüft die Logs:

    docker compose logs opensearch-node1
docker compose logs opensearch-init

  7. Merkt euch die beiden Kommandos zum Aufräumen:

    docker compose down      # Container stoppen, Daten im Volume bleiben
docker compose down -v   # Container UND Daten löschen - der Reset-Knopf

Teil 2: Cluster prüfen

  1. Öffnet im Browser: https://localhost:9200

    • Benutzername: admin
    • Passwort: (aus der .env-Datei)
    • Akzeptiert das selbstsignierte Zertifikat
    • -> Welche Version und welche Lucene-Version zeigt die Antwort?

  2. Öffnet OpenSearch Dashboards: http://localhost:5601

    • Meldet euch mit denselben Zugangsdaten an
    • Navigiert zu Dev Tools (Menü links -> Management -> Dev Tools)

  3. Führt in der Dev Tools Console folgende Abfragen aus:

    Cluster-Gesundheit prüfen:

    GET _cluster/health

    -> Welchen Status hat der Cluster? (green/yellow/red) Wie viele Nodes sind erkannt?

    Nodes anzeigen:

    GET _cat/nodes?v

    -> Sind beide Nodes sichtbar? Welche Rollen haben sie? Welcher Node ist mit * als Cluster Manager markiert?

    Vorhandene Indizes prüfen:

    GET _cat/indices?v&s=index

    -> Welche Indizes beginnen mit einem Punkt, und wozu gehören sie? Welche Indizes enthalten schon Daten?

    Cluster-Einstellungen:

    GET _cluster/settings?include_defaults=true&flat_settings=true

    -> Sucht in der Ausgabe nach cluster.max_shards_per_node. Wie viele Shards erlaubt ein Node?

Teil 3: Vorgeladene Daten prüfen

Der Container opensearch-init hat beim Start zwei Datensätze über die Bulk API geladen. Diese Daten sind die Grundlage für die Übungen 3 bis 8.

GET apache-logs/_count

-> Erwartet: 10.012 Dokumente (Apache Access Logs)

GET rezepte/_count

-> Erwartet: 12.190 Dokumente (Rezepte mit deutschem Analyzer)

Schaut euch ein Beispieldokument aus jedem Index an:

GET apache-logs/_search
{
  "size": 1
}

GET rezepte/_search
{
  "size": 1
}

-> Die Apache-Logs wurden beim Laden durch eine Ingest Pipeline geparst. Welche strukturierten Felder erkennt ihr, die in einer Logzeile so nicht stehen?

Wenn die Zahlen nicht stimmen: Prüft mit docker compose logs opensearch-init, ob das Laden durchgelaufen ist. Ein vollständiger Neustart mit docker compose down -v und docker compose up -d lädt die Daten erneut.

Teil 4: Erste Dokumente indexieren

  1. Indexiert das erste Produkt aus Übung 1 über Dev Tools:

    PUT /produkte/_doc/1
{
  "name": "OpenSearch T-Shirt",
  "kategorie": "Merchandise",
  "preis": 29.99,
  "verfuegbar": true,
  "tags": ["opensearch", "merch", "clothing"],
  "bewertung": {
    "durchschnitt": 4.5,
    "anzahl": 120
  }
}

    -> Was steht im Feld result der Antwort? Führt den Aufruf ein zweites Mal aus - was ändert sich?

  2. Ruft das Dokument ab und prüft, ob es korrekt gespeichert wurde:

    GET /produkte/_doc/1

  3. Indexiert die restlichen Produkte per Bulk API - nutzt dazu das NDJSON-Format:

    POST _bulk
{"index": {"_index": "produkte", "_id": "2"}}
{"name": "Dashboard Handbuch", "kategorie": "Bücher", "preis": 39.50, "verfuegbar": true, "tags": ["opensearch", "dashboards", "dokumentation"], "bewertung": {"durchschnitt": 4.2, "anzahl": 45}}
{"index": {"_index": "produkte", "_id": "3"}}
{"name": "Cluster Monitoring Poster", "kategorie": "Merchandise", "preis": 14.99, "verfuegbar": false, "tags": ["opensearch", "monitoring", "poster"], "bewertung": {"durchschnitt": 3.8, "anzahl": 12}}

    Wichtig: Der Bulk-Request muss mit einer leeren Zeile enden!

  4. Prüft den Index:

    GET _cat/indices/produkte?v

    -> Wie viele Dokumente enthält der Index?

  5. Schaut euch an, welche Feldtypen OpenSearch automatisch gewählt hat:

    GET produkte/_mapping

    -> Welchen Typ hat preis? Welchen Typ hat name, und welches Unterfeld ist dazu entstanden? Wir kommen in Übung 4 darauf zurück.

Teil 5: Monitoring prüfen

  1. Öffnet Prometheus: http://localhost:9090

    • Navigiert zu Status -> Targets
    • Es gibt zwei Jobs: prometheus (Prometheus selbst) und opensearch mit beiden Nodes
    • Prüft, ob die beiden OpenSearch-Targets den Status UP haben
    • Der abgefragte Endpunkt ist /_prometheus/metrics aus dem Prometheus-Exporter-Plugin

    Bei Status DOWN mit 401: Das Passwort in data/prometheus.yml stimmt nicht mit dem in der .env überein.

  2. Öffnet Grafana: http://localhost:3000

    • Login: admin / admin - Grafana fragt danach nach einem neuen Passwort, das könnt ihr für die Schulung überspringen
    • Prüft unter Dashboards, ob ein vorkonfiguriertes OpenSearch-Dashboard vorhanden ist
    • Welche Metriken werden angezeigt? (z.B. JVM Heap Usage, Indexing Rate)

Erwartete Ergebnisse

  • 6 Container laufen (docker compose ps zeigt Status Up), opensearch-init ist beendet
  • Cluster-Status ist green, beide Nodes (opensearch-node1, opensearch-node2) sind sichtbar
  • Version 3.7.0 wird gemeldet
  • apache-logs enthält 10.012 und rezepte 12.190 Dokumente
  • 3 Produkte im Index produkte indexiert
  • Das automatisch erzeugte Mapping von produkte ist bekannt
  • Prometheus-Targets UP, Grafana-Dashboard erreichbar

Wiederholung

REST-API-Verben in OpenSearch

HTTP-Verb Verwendung in OpenSearch Beispiel
GET Daten abrufen, Suchen GET /produkte/_doc/1
PUT Dokument mit ID erstellen/ersetzen PUT /produkte/_doc/1 {...}
POST Dokument ohne ID erstellen, Bulk, Suchen POST _bulk {...}
DELETE Dokument oder Index löschen DELETE /produkte/_doc/1
HEAD Existenz prüfen (ohne Body) HEAD /produkte

Cluster-Status-Farben

Farbe Bedeutung
Green Alle Primary- und Replica-Shards sind zugewiesen
Yellow Alle Primary-Shards zugewiesen, aber Replicas fehlen
Red Mindestens ein Primary-Shard ist nicht zugewiesen

Die Container der Schulungsumgebung

Container Aufgabe
opensearch-node1 Datenknoten, per Port 9200 und 9600 von außen erreichbar
opensearch-node2 Datenknoten, nur im Docker-Netz erreichbar
opensearch-dashboards Web-Oberfläche auf Port 5601
opensearch-init lädt die Beispieldaten und beendet sich
logstash wird in xx Abschlussprojekt und im Logstash-Block genutzt
prometheus sammelt Metriken auf Port 9090
grafana zeigt die Metriken auf Port 3000

Tipps & Ressourcen

Vorgehen

  • Startet die Container immer mit -d (detached), damit das Terminal frei bleibt
  • Bei Zertifikatsfehlern im Browser: https:// verwenden und Warnung akzeptieren
  • Für curl-Anfragen an OpenSearch: curl -k -u admin:<passwort> https://localhost:9200
  • docker compose logs -f <container> zeigt die Logs laufend mit - das erste Werkzeug bei jedem Problem
  • Node 2 zeigt in docker compose ps keine Ports mit 0.0.0.0 - das ist beabsichtigt, er ist nur intern erreichbar

Troubleshooting

Problem Lösung
Container startet nicht docker compose logs <container> prüfen
Node beendet sich sofort .env fehlt oder Passwort zu schwach - cp env.example .env
Image-Build schlägt fehl Kein Netzzugang zu GitHub für das Exporter-Plugin, ggf. Proxy setzen
max virtual memory areas Fehler Linux/WSL: sudo sysctl -w vm.max_map_count=262144. Docker Desktop auf macOS/Windows setzt das in der eigenen VM bereits
Port bereits belegt lsof -i :9200 und konkurrierenden Prozess stoppen
Dashboards zeigt Fehler Warten bis die Nodes vollständig gestartet sind (ca. 30-60s)
Zertifikatsfehler bei curl Flag -k verwenden um die SSL-Verifikation zu überspringen
Daten fehlen (apache-logs leer) docker compose logs opensearch-init prüfen, dann down -v und neu starten
Prometheus-Target DOWN (401) Passwort in data/prometheus.yml an die .env angleichen
